1. Document Purpose
This document is the master development brief that the user can provide to ClaudeCode to design, scaffold, document, and iteratively improve the bot.
The deliverable is a learning-first crypto bot that connects to Binance, Bybit, and Bitget, ingests account and market data, manages spot and futures state, and runs in three modes: observation, paper trading, and controlled live evaluation.
The rebuilt system must be modular, testable, auditable, and easy to disable or restrict if live metrics deteriorate.
2. Mandatory Non-Goals
Do not build an unrestricted self-modifying autonomous trading agent.
Do not allow ClaudeCode to place orders directly, override risk rules, widen stops, raise leverage, or force wallet transfers.
Do not implement martingale, averaging down, revenge trading, or any automatic behavior that attempts to recover losses by increasing risk.
Do not enable live auto-transfers between spot and futures until the futures engine demonstrates positive expectancy in paper trading and controlled testing.
3. Supported Exchanges and Scope
Exchanges: Binance, Bybit, Bitget.
Markets: Futures and Spot state monitoring. Futures strategy is the primary active module; spot is managed conservatively through hold / trim / exit / rotate recommendations.
Primary live/paper symbol universe for rebuild: BTCUSDT and ETHUSDT only, with an optional third major added later if the data supports it.
Preferred futures style for research: active scalp logic, but filtered aggressively and validated against historical data before live usage.
4. Required Operating Modes
Observation Mode: collect all balances, positions, orders, fills, market features, and candidate setups. No live orders are sent.
Paper Trading Mode: simulate deterministic entries and exits using realistic fee and slippage assumptions. Log all hypothetical trades.
Controlled Live Mode: limited live testing with strict caps, narrow symbol universe, and kill-switch protection. This mode must be disabled by default unless explicit config approval is present.
5. High-Level Architecture
Exchange Adapter Layer: unified wrappers for Binance, Bybit, and Bitget. Responsibilities: authentication, symbol normalization, balances, positions, orders, trade history, market data retrieval, and rate-limit handling.
Market Data Engine: collect OHLCV, top-of-book data, spread, volatility metrics, funding rate, and depth summaries on configurable intervals.
Portfolio State Manager: maintain the current state of futures balances, spot holdings, average buy price, realized and unrealized PnL, position exposure, and available transfer state.
Base Signal Engine: generate deterministic candidate setups only when the regime allows them.
Feature Extractor: convert every candidate setup and executed trade into a structured feature vector suitable for analysis and meta-filtering.
Meta-Filter: decide whether a candidate setup should be allowed, skipped, or size-reduced based on historical performance patterns and interpretable rules/models.
ClaudeCode Advisory Layer: perform historical labeling, pre-trade contextual review, weekly diagnostics, and behavior drift detection.
Risk Engine: position sizing caps, leverage caps, daily loss stops, symbol pauses, strategy pauses, spread/slippage guards, and global kill-switches.
Execution Engine: paper execution simulator plus optional live execution module with limit-first behavior and mandatory stop logic.
Analytics & Reporting: dashboards, logs, alerts, and exportable reports for expectancy, profit factor, drawdown, slippage, fees, and trade quality.
6. Historical Data Warehouse Requirements
Create a persistent database to store every historical executed trade and every candidate setup produced by the bot, whether traded or skipped.
Minimum fields per trade: exchange, market type, symbol, side, strategy family, regime label, entry timestamp, exit timestamp, entry price, stop price, target price, size, leverage, fee, slippage, realized PnL, unrealized PnL snapshot at intervals, result in R, hold time, order type, and status.
Minimum environment fields: spread percentile, volatility percentile, funding rate, order-book imbalance, depth estimate, time of day, day of week, exchange identifier, and recent loss-streak state.
Store ClaudeCode review outputs (decision, confidence, red flags, reason labels, commentary) for both historical annotation and future auditability.
7. Historical Learning Workflow
Import all old trades into the warehouse first.
For each historical trade, reconstruct as many entry-time features as possible from stored logs or exchange history.
Send a structured summary of each trade to ClaudeCode for reason labeling. Suggested labels: valid_setup, invalid_setup, regime_mismatch, weak_symbol, low_liquidity, spread_risk, slippage_risk, volatility_trap, late_entry, overtrading, avoidable_loss, unavoidable_loss.
Build analysis jobs that rank losses by symbol, exchange, setup family, time window, spread regime, and volatility regime.
Use the findings to derive skip rules, cooldown rules, and tighter guardrails before any live execution resumes.
8. Meta-Filter Specification
Purpose: predict the quality of a candidate trade, not the next price move directly.
Inputs: candidate setup features, market context features, account state, current loss streak, exchange identifier, symbol identifier, and recent execution quality metrics.
Outputs: ALLOW, SKIP, or REVIEW, plus optional size modifier capped by the risk engine.
Start with interpretable logic (threshold rules, scorecards, or simple supervised models) before considering more complex models.
The meta-filter must support offline backtesting and walk-forward evaluation. No unsupervised live self-modification.
9. Deterministic Base Strategy Requirements
Implement only a small number of deterministic setup families. Suggested initial families: momentum pullback scalp and range rejection scalp, each with clear, auditable entry and exit criteria.
Every setup must be disabled automatically in blocked regimes such as news-like volatility expansion, abnormal spread, or dead market conditions.
No breakout chasing, no averaging down, no discretionary leverage changes, and no implicit “hold and hope” conversion of failed scalps into longer holds.
Candidate setups should be generated even in observation mode so the system can learn from both traded and skipped opportunities.
10. ClaudeCode Advisory Integration
Historical Review Task: ClaudeCode labels historical trades and candidate setups with reason tags and short explanations.
Pre-Trade Review Task: for a candidate setup that passes deterministic rules, ClaudeCode receives a structured payload and returns decision, confidence, red_flags, reason_labels, and commentary.
Weekly Diagnostic Task: summarize best and worst symbols, exchanges, setup families, regimes, hours, fee drag, and slippage problems.
Drift Detection Task: compare recent setup distribution and trade behavior against the historical profile of the bot’s best-performing setups.
All ClaudeCode outputs must be machine-validated against a strict schema before they are accepted.
11. Example ClaudeCode Schemas
Historical annotation output schema: decision, confidence, reason_labels, commentary.
Pre-trade review output schema: decision (ALLOW | SKIP | REVIEW), confidence (1-5), red_flags (list), commentary (string).
Weekly diagnostic output schema: top_loss_drivers, top_win_drivers, symbols_to_disable, setup_families_to_review, exchange_health_notes, summary.
Drift detection output schema: drift_level (LOW | MEDIUM | HIGH), mismatched_features, commentary, recommended_action.
12. Risk Engine Requirements
The risk engine must be hard-coded and must take precedence over every other module.
Required controls: max risk per trade, max leverage, max concurrent positions per exchange, max concurrent positions per symbol, daily loss limit, consecutive-loss pauses, abnormal spread pause, stale-data pause, repeated rejection pause, and global kill-switch.
If live mode is enabled, after 2 consecutive losses on the same symbol, pause that symbol; after 3 consecutive losses in the same setup family, pause that setup family; after 5 global consecutive losses, switch to observation or paper mode automatically and require review.
Implement explicit outlier-loss containment. A single failed execution or volatile event must not be able to exceed a predefined maximum loss cap.
13. Spot Portfolio Module Requirements
Pull all spot holdings from connected exchanges, including average buy price where available or reconstructable.
Compute current PnL, trend state, concentration risk, and opportunity cost for each spot asset.
Allowed recommendation actions: HOLD, TRIM, EXIT, ROTATE_TO_USDT.
No hedging in this version. No autonomous futures funding from spot during the rebuild phase unless explicitly approved in config after paper validation.
14. Execution Requirements
Separate paper execution and live execution into different modules and different config profiles.
Live execution must be disabled by default.
Prefer limit-first execution when feasible, but all execution behavior must be configurable and thoroughly logged.
Stops must be attached or validated immediately after order acknowledgement. Failed stop placement must trigger emergency handling and alerting.
Never silently continue after failed order placement, stale market data, or inconsistent position state.
15. Logging, Monitoring, and Analytics
Log every candidate setup, every ClaudeCode response, every risk-engine decision, every order event, every fill, and every pause reason.
Dashboard metrics must include: trades count, win rate, average win/loss, expectancy, profit factor, drawdown, fees, slippage, loss streaks, symbol-level performance, exchange-level performance, and strategy-family performance.
Include a “what would have happened” comparison for: raw deterministic strategy vs meta-filtered strategy vs ClaudeCode-vetoed strategy.
Provide exportable CSV/JSON summaries for weekly and monthly review.
16. Project Structure Recommendation
Suggested top-level modules: config, adapters, data, signals, features, meta_filter, claude_integration, risk, execution, portfolio, analytics, storage, api, tests, and docs.
Provide environment-based configuration for observation, paper, and live modes.
Keep exchange credentials and model keys in secure environment variables or secrets storage; do not hardcode keys.
17. Testing and Validation Requirements
Unit tests: exchange normalization, risk checks, schema validation, feature extraction, and state transitions.
Integration tests: paper execution flow, ClaudeCode schema handling, order failure handling, and pause logic.
Backtesting / replay tests: run historical candidate setups with and without meta-filter and ClaudeCode review.
Walk-forward tests: validate that any improvement persists on unseen data segments.
Acceptance criteria for controlled live mode: positive rolling expectancy, profit factor above 1.0 on a meaningful sample, stable drawdown profile, and no uncontrolled outlier loss behavior.
18. Implementation Phases for ClaudeCode
Phase 1 — Project scaffolding: repository structure, config system, exchange adapter interfaces, storage schema, and logging framework.
Phase 2 — Data ingestion: balances, positions, orders, market data, and historical trade import.
Phase 3 — Observation mode: candidate setup generation, feature extraction, and database persistence.
Phase 4 — ClaudeCode annotation pipeline: historical labeling, schema validation, and audit logging.
Phase 5 — Meta-filter: initial interpretable skip/allow engine and offline evaluation tools.
Phase 6 — Paper trading engine: simulated fills, fees, slippage, and comparison reports.
Phase 7 — Risk engine hardening: kill-switches, pauses, outlier controls, and alerting.
Phase 8 — Controlled live integration: disabled by default; enable only after documented approval and passing acceptance tests.
19. Explicit Instructions to ClaudeCode
First, read this document and summarize the architecture back in a concise implementation plan.
Second, scaffold the repository with placeholder modules, config templates, data models, and schema validators.
Third, implement observation mode and paper trading mode before any live execution code path.
Fourth, create the historical data warehouse, import scripts, and trade-labeling pipeline.
Fifth, build the meta-filter and analytics dashboards needed to compare raw strategy results against filtered results.
Sixth, do not enable live trading by default and do not include any code path that bypasses the risk engine or ClaudeCode schema validation.
Seventh, document every module, every schema, and every operating mode clearly so the owner can audit behavior before any live testing.

21. Final Instruction
Treat this project as a learning-first rebuild of a currently loss-making system. Prioritize traceability, testing, and risk containment over feature count or trading frequency.
If any requirement in this document conflicts with a profit-seeking shortcut, the risk-managed requirement wins.
